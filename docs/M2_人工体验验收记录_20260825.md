## 发现的问题

### P0：技能内部结构化提示暴露在用户消息中

四个技能均将包含玩法边界、固定免责声明、原始主题或月日，以及内部生成指令的完整结构化文本写入聊天记录。它既破坏沉浸式对话，也与“结果卡不回显原始输入”的既定要求不一致；窄屏时该长文本占据了大部分可视区域。

建议：服务端仍可向模型传递结构化上下文，但保存和渲染给用户的消息应替换为简短、自然、且不回显原始输入的技能启动语，例如“我来为你抽一张牌，看看这个主题能带来什么联想。”

### P1：星座输入格式反馈不够明确

输入“5月20日”会被拒绝，仅显示“提交的信息有误，请检查后重试”；输入 `05-20` 后可成功。界面标签为“生日（月日）”，但没有示例或格式提示。

建议：在输入框给出 `例如：05-20` 的格式示例，或同时兼容“5月20日”。

### P1：技能回复的开发 Mock 缺少技能差异

在未配置真实/本地模型的开发环境中，四种技能都返回相近的通用追问，结果卡本身正常。该项不影响流程正确性，但不足以评估角色和技能的陪伴感；接入本地模型或后续免费 Provider 后应重新验收。

### P2：桌面内容密度仍是结构性布局

桌面宽屏中，会话区域横向留白较大，消息与结果卡集中在左侧窄列；这使聊天软件的沉浸感不足。窄屏结构可用，但 P0 长提示进一步压缩有效内容区域。

这属于尚未最终定稿的 UI 视觉设计范围，应在后续视觉设计任务中统一处理，而不是在 M2 功能分支做局部样式堆叠。

## 结论

四项技能的流程和卡片功能通过人工路径验证，但 P0 问题阻止 M2 作为沉浸式聊天体验完成合并验收。建议先修复 P0，再复测四项技能、桌面与窄屏布局；P1/P2 可纳入同一轮体验优化或明确列入后续 UI/模型任务。
